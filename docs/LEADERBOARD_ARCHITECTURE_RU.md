# Глобальный рейтинг RULESHIFT: архитектура

Финальная локальная подготовка UI, interrupted journal и session revocation: [LEADERBOARD_FINAL_PREP_RU.md](LEADERBOARD_FINAL_PREP_RU.md). Реальный Cloudflare QA ещё не выполнен.

Актуальная реализация backend описана в [LEADERBOARD_BACKEND_PROGRESS_RU.md](LEADERBOARD_BACKEND_PROGRESS_RU.md): passkeys/recovery, привязка GameRoom, durable outbox, D1 settlement и API добавлены локально. Вместо отдельного Rankings Worker/coordinator используется существующий Worker/GameRoom и атомарный D1 batch с optimistic revision. Runtime D1 и браузерные passkeys пока не подтверждены; NO-GO для готового staging backend. Текущий protocol v8. Ниже сохранён первоначальный архитектурный проект и прежний статус для контекста; заявления «ещё не подключено» относятся к состоянию до этой реализации.

Статус на 2026-10-09: **частичная локальная подготовка**. Пользователь согласовал passkeys + одноразовые коды восстановления без обязательного email. Подготовлены `migrations/leaderboard/0001_accounts_ratings.sql`, кандидат формулы `src/shared/rating.ts` и тесты на изолированном SQLite. Авторизация, settlement/outbox и API ещё не подключены. UI показывает недоступность сервиса. Топ-100, поиск позиции, аккаунты и сезонные результаты пока не работают. Никакие ресурсы Cloudflare не создавались. Текущий игровой протокол ветки — v8. Подробности и границы: [этап 4](OVERDRIVE_STAGE4_RU.md).

## Что существует

Клиент Vite/TypeScript/Phaser; серверные матчи — `Room` в `GameRoom` Durable Object, WebSocket protocol v6. Worker принимает создание комнаты и подключения через `/api/rooms`. Состояние и итог Online определяет сервер. Сейчас участник и reconnect secret привязаны к комнате, а не к постоянному аккаунту. Профиль, XP, 17 достижений, Offline-рекорды и Daily хранятся в localStorage. Они не являются защищёнными серверными наградами.

Staging имеет отдельный Worker и namespace ROOMS. MCP имеет отдельный Worker и не должен получать права записи в рейтинг. Production/staging должны также иметь разные будущие базы, сессии, ключи и auth origins. Данные staging не переносятся в production автоматически.

## Предлагаемые компоненты

1. Существующий игровой Worker — same-origin gateway для аккаунта и чтения рейтинга. Проверяет сессию до допуска в рейтинговый матч; обычные гостевые комнаты сохраняются.
2. Существующий GameRoom — авторитетная симуляция. При старте получает проверенную сервером привязку участник → accountId. Ник и JSON клиента не могут установить accountId.
3. Отдельный Rankings Worker — закрытый приём результатов через Service Binding, без публичного endpoint для начисления. Публичный gateway только читает таблицы.
4. Отдельная D1 для аккаунтов, credentials, сессий, журнала завершённых матчей, рейтингов и месячных сезонов. KV не используем как источник истины: нужна атомарная дедупликация и согласованное обновление.
5. Settlement coordinator Durable Object сериализует начисления; D1 batch/транзакция атомарно записывает журнал и обновляет всех участников. Перед реализацией проверить семантику rollback и optimistic concurrency на реальном runtime.

Предлагаемые таблицы: accounts (UUID, displayName, createdAt, status), credentials (public keys), sessions (hash token, expiry), challenges (one-use, expiry), matches (globalMatchId, mode, serverStart/end, seasonId, ruleVersion, status), participants (accountId, server placement, result, forfeit), settlement_ledger (unique match/account/rating bucket), ratings (account, mode/overall, lifetime/season, value, games/wins/losses/draws), seasons (UTC month, freeze status). Индексы по bucket/rating и account/bucket. Сортировка: rating DESC, rated games DESC, stable account ID; одинаковый рейтинг показывает одинаковую спортивную позицию, стабильный ID используется только для порядка выдачи.

## Аккаунт и несколько устройств

Рекомендуется WebAuthn/passkey вместо самодельных паролей. accountId — случайный серверный UUID, не ник. Проверять challenge, подпись, origin, rpId, user verification, короткий TTL и одноразовость challenge. Использовать проверенную библиотеку после отдельной оценки Workers-совместимости. Сейчас библиотека не добавлена.

Добавление второго passkey разрешено только после повторной аутентификации владельца. Синхронизируемый passkey или cross-device authentication позволяет вход с другого устройства; само наличие одинакового ника — никогда. Для восстановления: заранее выданные одноразовые recovery codes, сервер хранит только хеш; замена credentials отзывает все сессии. Без passkey/recovery нельзя восстановить аккаунт по никнейму. Email не обязателен; это снижает объём персональных данных, но требует понятного onboarding и предупреждения о потере recovery.

Сессия: случайный криптографический токен, хеш в D1; cookie HttpOnly/Secure/SameSite, ограничения срока и отзыв. State-changing запросы проверяют Origin и CSRF, CORS только разрешённый origin. Токен не попадает в URL, localStorage, логи или бандл. Постоянная статистика хранится в D1 после закрытия браузера; локальный профиль сохраняется отдельно, не импортируется как verified progress.

Игровой gateway передаёт verified account context в DO по внутреннему binding. Заголовки такого контекста, присланные извне, удаляются. Reconnect использует существующий секрет комнаты **и** тот же проверенный аккаунт. Два подключения одного аккаунта не создают двух участников рейтингового матча. Гости могут играть без рейтинга. HTTP-auth контекст можно добавить без изменения v6 сообщений; если auth/ranked поля становятся обязательными, потребуется отдельно согласованный protocol bump и тесты отказа старым клиентам.

## Авторитетный результат и защита от повтора

При старте сервер выдаёт глобальный случайный matchId, отдельный для каждого Rematch: room code и локальный номер матча сами по себе недостаточны. Участники, рейтинги до матча, версия формулы и UTC-сезон фиксируются сервером. Итог — только серверный receipt: не клиентские score, placement, XP или время устройства.

Завершение пишет receipt и pending settlement в durable outbox **до** подтверждения результата. Alarm повторяет доставку после сбоя. Coordinator принимает только внутренний вызов; D1 unique ledger исключает двойную запись при повторной доставке. В одном атомарном batch фиксируются матч, участники, дельты всех bucket и статус settled. Ответ/последующий retry не может повторить начисление. UI показывает pending до фиксации; ошибка рейтинга не должна отменять уже завершённый игровой матч.

Добровольный выход: forfeit по серверному решению. Обрыв сети: существующее окно reconnect, затем серверное решение; reconnect не создаёт новый результат. Нельзя обнулять поражение закрытием вкладки. Сбой Worker, при котором результат нельзя восстановить, означает unrated/void match, без выдуманного победителя. Существующий live-room snapshot ещё не является надёжным durable outcome ledger — outbox и восстановление надо реализовать и проверить.

## Кандидат формулы — до проверки баланса не применять

Рейтинги начинаются с 1000. Отдельные bucket: overall и четыре Online-режима; lifetime и UTC-месяц. Матч учитывается один раз в overall и один раз в выбранном mode, а не четыре раза. Месяц фиксируется при старте; законченный после полуночи матч относится к месяцу старта. Архив закрывается после ограниченного settlement grace period; поздние receipts требуют явной политики, а не незаметной правки архива. История lifetime не обнуляется.

Для n проверенных участников, n=2..8, использовать парное Elo:

`Eij = 1 / (1 + 10^((Rj − Ri)/400))`

`ΔRi = 24 / (n−1) × Σj≠i [ wij × (Sij − Eij) ]`

Sij = 1/0/0.5 для лучшего/худшего/равного серверного результата. Для текущих last-alive режимов: победитель выше остальных, остальные равны; не выдумывать места 2..8, если сервер их не фиксирует. Blitz: серверный score, затем существующий tie breaker; точные критерии сверить с Room до реализации. Forfeit ниже всех закончивших; несколько forfeits равны. Никаких дополнительных отрицательных дельт вне симметричной формулы.

wij симметричен: размер матча даёт коэффициент 0.5 для двух игроков, линейно до 1 для восьми; повтор одной пары за последние 24 серверных часа — 1, 0.5, 0.25, далее 0 (порог — кандидат). Так сумма дельт пары нулевая, повторные матчи не создают очки из ничего. Нужно хранить дробные значения, округлять только UI. Не вводить нижний clamp, создающий инфляцию. Forfeit фиксируется в lifetime stats даже если антифарм делает rated delta нулевой. Допуск ranked: минимум двух разных verified accounts, серверная фиксация участников и готовности до старта. Для обычного завершения — минимум длительности/реальных активных событий; случайный короткий match может быть void для всех. Добровольный forfeit после старта не становится void из-за короткой длительности: применяются обычные парные дельты и антифарм, иначе ранним выходом можно избегать поражения. До старта cancel не начисляет очки. Точные пороги требуют тестирования.

Один Rematch может быть честным новым матчем, но не обходит pair window. Локальная пауза/XP/Daily не влияют на формулу. Сезонный сброс не стирает anti-abuse историю. Сначала прогнать симуляции на 2–8 участников, ничьи/forfeit, различие режимов и навыка, инфляцию, pair cap, конкурентные receipts и rollover. Показать распределение результатов пользователю до включения.

Ограничения: passkey не доказывает «один человек = один аккаунт». Возможны Sybil, сговор, автоматические игроки, намеренные поражения и создание множества комнат. Pair cap уменьшает простой фарм, но не решает эти проблемы. Не объявлять систему защищённой от всех злоупотреблений. Пригласительные приватные комнаты разумно оставить unrated до проверки сговора/матчмейкинга.

## API и UI после согласования

`GET /api/leaderboard?mode=overall|classic|lastOneStanding|blitz|chaos&season=lifetime|YYYY-MM` — до 100 записей, snapshot timestamp, pagination budget. `GET /api/leaderboard/me` — позиция авторизованного аккаунта. `GET /api/seasons` — только реальные опубликованные сезоны. Нет публичного POST для результатов. Ник выводится escaped; accountId не раскрывает credentials/PII. Кэш топа 30–60 секунд с version/ETag; собственная позиция private/no-store. Источник данных и время обновления видны пользователю.

## Лимиты, удаление и наблюдаемость

Глобальный rate limit на gateway, не только существующая isolate-local Map. Предварительные бюджеты: чтение таблицы 30/min IP, auth challenge 10/min IP, verify 5/min IP/account, создание 6/min account; лимиты на число одновременных комнат и pending settlements. Это параметры для нагрузки, не реализованная защита. Body/WS limits, one-use challenge, anti-replay и bounded pagination обязательны. CAPTCHA/Turnstile при риске, не требовать для обычных кадров игры. Длинные очереди отслеживать, не делать unbounded retries.

Не хранить email, геолокацию, fingerprint; IP в антиабьюзе — короткий TTL и keyed hash с ротацией. Логи без cookies, reconnect secrets, passkeys, recovery codes, MCP_KEYS. Учесть, что public nickname — пользовательские данные. Удаление аккаунта после повторного подтверждения отзывает сессии, удаляет credentials, профиль, rank/stats и участие из публичного архива. Для уже обработанных receipts хранить минимальный непубличный tombstone/случайный ID на документированный срок: late retry не должен воскресить удалённый аккаунт. Unknown/deleted account запрещён для settlement. До запуска согласовать retention, экспорт данных, сроки резервных копий и удаление зависимых строк.

## Cloudflare: оценка на 2026-10-09

Тарифы сверены с официальными страницами; это оценка, не проверка плана аккаунта. Paid Workers от $5/месяц: 10 млн запросов и 30 млн CPU-ms включены; дальше $0.30/млн запросов и $0.02/млн CPU-ms. Static Assets сами по себе бесплатны. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/).

DO Paid: 1 млн запросов и 400 тыс. GB-s включены; сверх — $0.15/млн запросов и $12.50/млн GB-s, с округлением оплачиваемого объёма вверх. Входящие WS-сообщения считаются 20:1, исходящие не оплачиваются как requests. Duration учитывает выделенные 128 MB, не измеренный heap. Активный игровой таймер не даёт рассчитывать на hibernation. [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

D1 Paid: 25 млрд прочитанных и 50 млн записанных строк/месяц, 5 GB включены; сверх $0.001/млн чтений, $1/млн записей и $0.75/GB-month. Индексы увеличивают записи; top/rank queries должны иметь проверенный query plan. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).

Пример допущений: 1000 DAU × 3 матча × 30 дней = 90 тыс. player appearances. При четырёх участниках и 120 сек на матч: 22.5 тыс. room matches, 2.7 млн room-seconds ≈345600 GB-s. Текущий клиент отправляет input каждые 50 ms: ≈216 млн входящих сообщений /20 =10.8 млн DO requests плюс joins/прочее. При свободных включённых квотах приблизительно $1.50 за DO requests сверх квоты; duration в квоте; базовый Paid итого около $6.50 **до** CPU, SQL, лобби, reconnect, долговременных idle connections, округлений других метров и нагрузки production/MCP. Это не прогноз счёта; расходы нового рейтинга D1 обычно ниже live-game DO, но замеры обязательны.

Free ограничен по дням: Workers 100 тыс. requests/day, DO 100 тыс. requests/day и 13000 GB-s/day; D1 5 млн rows read/day и 100 тыс. written/day, total 5 GB. При превышении операции могут перестать работать. Этот пример превышает DO request Free budget, поэтому обещать «бесплатно для 1000 DAU» нельзя. Paid квоты разделяются с другими Workers аккаунта. Проверить billing в dashboard, настроить alerts, API CPU limits и лимит создания комнат; alert сам по себе не hard spending cap. Не включать cron обход всех комнат или SQL запись каждого игрового тика ради рейтинга.

## Offline и Daily

Остаются личными localStorage-рекордами. Deterministic seed не подтверждает исполнение честным клиентом. Будущая проверка: server-issued challenge/date/nonce + bounded input replay, серверный re-simulation с версией движка, clock/rate constraints и deadline; отдельно изучить стоимость и automation/ботов. Не принимать итоговый score как доказательство. Даже валидный replay не доказывает человеческую игру. До этого Offline/Daily исключены из глобальных очков и серверных наград.

## Решения, требующие согласования

Passkeys + recovery без обязательного email; D1 + закрытый Rankings Worker + settlement DO; какие комнаты eligible (рекомендация: публичный ranked, приватные unrated); кандидат Elo/pair cap/minimum qualification; UTC season grace и retention; бюджет Paid и лимиты. Только после согласования — реализация auth/outbox/storage, тесты на Workers runtime и ограниченный staging QA. SQL migration, bindings и secrets в этом этапе не добавлены.
