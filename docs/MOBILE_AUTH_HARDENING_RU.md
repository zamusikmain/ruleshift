# Мобильная авторизация — локальные исправления, 10 октября 2026

Ветка feature/ruleshift-2-chaos-update. Deployment, миграций и изменений секретов в этом этапе нет.

## Причина и границы диагностики

Точная причина 6–7 отказов на iPhone пока **не установлена**: нет HTTP-статусов и callback-логов этих конкретных попыток. Не следует объявлять причиной ITP, cookies или Google без воспроизведения.

Подтверждены дефекты клиента:

- Google start выполнялся через общий action, который после location.assign снова запускал providers/me и снимал блокировку кнопок. Повторное нажатие могло создать новый flow и заменить OAuth cookie предыдущего flow. Это реальная возможность гонки, но её участие в сообщённом сбое Safari не доказано.
- Ошибки load(), включая HTTP 403/429 и неверный ответ, маскировались текстом ошибки сети.
- fetch не имел ограничения ожидания.
- Первоначальное сохранение имени не завершало onboarding, требовалась дополнительная кнопка.

Worker проверен по коду: callback `/api/auth/google/callback`, state одноразовый, PKCE S256, nonce и подпись/issuer/audience/expiry ID token проверяются. Cookie OAuth — __Host, Secure, HttpOnly, Path=/, SameSite=Lax; сессия — Secure/HttpOnly/SameSite=Strict. Запросы API same-origin, POST проверяет Origin. Эти проверки не изменены.

ITP нельзя диагностировать по одному сообщению об ошибке. Источники: [WebKit Tracking Prevention](https://webkit.org/tracking-prevention/) и [Google OAuth web-server flow](https://developers.google.com/identity/protocols/oauth2/web-server).

## Изменения

- src/accountView.ts: защита повторного нажатия сохраняется при переходе к Google; лишний load после assign удалён. Если переход не состоялся за 20 секунд, появляется ошибка таймаута и доступна повторная попытка без автоматического запуска OAuth. Ошибки сети, таймаута, ограничения частоты, сервера и запрета различаются.
- src/leaderboardApi.ts: AbortController, 20 секунд на один запрос включая тело ответа; таймер очищается; автоматических повторов POST нет. Таймаут записи не означает, что сервер гарантированно ничего не сохранил: состояние нужно сверить повторным чтением.
- Первоначальный выбор ника: только имя и «Сохранить и продолжить». После подтверждения rename сервером обновляется профиль и открывается меню. Ошибка оставляет экран открытым. Готовый аккаунт при startup переходит в меню автоматически. Редактирование из профиля остаётся в профиле. Recovery codes по-прежнему требуют подтверждения сохранения.
- src/locales/en.ts, ru.ts: локализованные кнопка и ошибки.
- scripts/auth-diagnostics.mjs: безопасный просмотр метаданных tail только staging. Выводятся allowlisted путь без query, HTTP status, outcome и существующий безопасный callback reason. Не выводятся cookies, URL Google, коды, ID token, email, заголовки или произвольные сообщения.
- tests/leaderboard-ui.test.mjs, auth-network.test.mjs, load.mjs: регрессии навигации, дублей, таймаутов, первого ника, серверной ошибки, профиля, RU и фильтра диагностики; тестовая VM получает стандартные AbortController/таймеры браузера.

## План iPhone Safari: минимум 10 отдельных входов

Сначала отдельно разрешить staging deployment. Затем на ПК в папке проекта:

```powershell
node scripts/auth-diagnostics.mjs
```

На iPhone открыть staging в обычном Safari (не встроенном браузере), оставить штатную защиту Safari включённой. Для каждого входа нажимать кнопку Google **один раз**; между попытками выполнить logout в профиле. Не удалять аккаунт, не очищать рейтинги, не пересылать HAR, cookies, Google URL или секреты.

1. Вход нового пользователя; выбор ника; «Сохранить и продолжить» → меню без второй кнопки.
2. Тот же аккаунт: повторный вход → меню без выбора ника.
3. Вход, reload → тот же аккаунт/ник/рейтинг.
4. Вход после закрытия и открытия вкладки.
5. Гость → Google: локальные достижения сохранены, аккаунт прежний.
6. Google → logout → гость → Google.
7. Вход и изменение ника из профиля без выхода в меню.
8. Вход по Wi-Fi; проверить портрет, клавиатуру и доступность кнопки.
9. Вход по мобильной сети; проверить альбомную ориентацию и safe areas.
10. Вход при медленном соединении: конечное loading/error, управляемая повторная попытка, отсутствие параллельных процессов.

Между быстрыми попытками выдерживать минимум минуту: существующий auth rate limit общий для IP, несколько запросов одного входа расходуют лимит. HTTP 429 — ожидаемая защита; не считать её случайным отказом Google. Отдельно проверить потерю сети и временный серверный отказ без отключения D1: эти негативные сценарии уже проверены тестовыми ответами, реальную недоступность инфраструктуры не провоцировать.

Для каждой попытки записать номер, время с часовым поясом, iOS/Safari, Wi-Fi/мобильную сеть, появился ли экран Google, результат, длительность, точный текст ошибки. Из безопасного tail сопоставить route/status/reason. Если отказ произошёл до Worker, tail может не показать запрос: тогда причина ещё не доказана. Нужна совместная контролируемая попытка, а не серия повторных нажатий.

Критерий: 10/10 входов при исправной сети, без повторных нажатий; nickname onboarding завершён; reload сохраняет аккаунт, рейтинг и локальный прогресс. Наличие клавиатуры, safe areas, ITP и мультитач подтверждается только устройством.
